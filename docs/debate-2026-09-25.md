## 3. What the brief and the FAQ ask for, and what this architecture delivers on P0

**What is asked.**
- The brief's P0: "Given a library of code and a query in natural language, provide a ranking of the code snippets". It lists "Pre/post processing of the code snippets" as a route to improvement, and says the solution is "expected on run on CPU with minimal GPU resource utilization".
- The FAQ is sharper on three points:
  - "The theme focuses on pre/post processing and we don't expect the choice of a embedding/retrieval model to have a significant impact."
  - "Dynamic analysis, such as execution of code is also in scope and allowed, however keep in mind that your approach should ideally generalize".
  - The unseen hands-on set will be "representative of the APPS dataset" and "also in Python".

The FAQ therefore rewards CPU post-processing that transfers to APPS-like data. That is exactly what execution verification is.

**Where the screening number comes from.** These are the repo's own logged test runs, which I read but did not recompute (`data/test_split_audit_log.json`):

| Configuration | NDCG@10 |
|---|---|
| Dense only | 0.93756 |
| + execution, depth 10 | 0.96085 |
| + execution, depth 20 | 0.96543 |
| + numeric output comparison | 0.96558 |

So 0.028 of the 0.96558 comes from post-processing. The other 0.938 is the encoder.

**My measurements on held-out training data** (never the test split). I used the `competitive_stdin` family because the repo reports the test split as about 99% stdin; I could not verify that without the test texts.

- **The gain is large and one-sided.**
  - 1.7B DEV: dense 0.90155 → shipped rule 0.95978, a gain of +0.0582 [+0.0462, +0.0709].
    - 102 statements change: 99 improve, 3 get worse.
    - 93 golds move to rank 1; 3 lose rank 1.
    - Sign-flip p &lt; 1e-4.
  - TUNE replicates it: +0.0484 [+0.0377, +0.0594], with 85 improving and 3 worse.
- **It captures most of the reachable gain.** "Headroom" here means the NDCG@10 that would be reached if every gold already in the dense top 20 were moved to rank 1. On DEV the shipped rule captures 71.5% of that headroom (0.0582 of 0.0815); on TUNE, 64.8%.
- **It tells the right problem from the wrong one.** Of the gold solutions it executes, 601 of 798 verify (75%). Only 144 of 15,462 other-problem candidates verify (0.9%).
- **It is worth more than a bigger encoder.** 0.6B dense plus execution (0.93924) beats 1.7B dense alone (0.90155) by +0.0377 [+0.0253, +0.0510] on 882 paired statements. A CPU post-processor outperforms an encoder 2.8 times larger. That is the kind of value the FAQ says the theme is about.
- **It transfers beyond APPS.** On CodeContests EXT-dev (108 statements; APPS corpus plus same-problem correct and incorrect solutions):
  - 1.7B: +0.0336 [+0.0044, +0.0633], p = 0.030.
  - 0.6B: +0.0430 [+0.0173, +0.0712], p = 0.002.
  - The rule has few parameters and none is APPS-specific: depth 20, 2 examples, a 2 s timeout, a numeric tolerance of 1e-6.
- **It is cheap on CPU.**
  - I ran the shipped rule live on 40 seeded DEV statements with 4 workers: 0.62 s per statement on average (median 0.49, p95 1.31, max 2.26).
  - This laptop was shared with another executive's jobs, and the sandbox timeouts are wall-clock, so these timings depend on load.
  - For reference only, since it is a different machine and not a ratio I claim: the repo measured 1.7B query encoding at 7.83 s per query on a 2-core Kaggle CPU (`cpu_latency.json`).
- **The offline replay is trustworthy.** On a sample drawn with my own seed (777), live sandbox runs matched the replayed top-10 in 40 of 40 statements for both the call-style and the deepened rule.

## 4. Where the case against is strongest (conceded)

1. **The encoder carries most of the number.** On test, going from the 0.6B to the 1.7B dense encoder is worth +0.033 (0.90427 → 0.93756, audit log). That is more than the whole post-processing gain of +0.028, which runs against the FAQ's expectation. The README says the encoder's exposure to APPS through OpenCodeReasoning-2 is plausible and unverified for any given problem.
2. **Near-misses cap the gain.**
   - On CodeContests, execution captures only 12.4% of the top-20 headroom (0.034 of 0.270).
   - Same-problem incorrect solutions sit at rank 1 in 61 of 108 statements under dense, and still in 54 after execution.
   - APPS has one document per problem: the corpus has 8,765 documents, which equals 5,000 train queries plus 3,765 test rows. Whether the unseen set does too is unknown. If it does not, most of the headroom is out of reach.
3. **The submitted run was inefficient.** Its `evaluation_time` is 12,855.69 s. The README admits the queries were encoded on a GPU, which conflicts with FAQ A ("ideally use the CPU only"). This comes from the 1.7B encoder, not the execution pass. The repo's own estimate is about 8.2 h to encode the queries on 2-core CPU.
4. **The v2 branch adds about 0 to the screening number.** On DEV stdin the candidate config scores the same as the frozen one (0.95978 both). Its measured gain is on call-style statements: +0.0041 overall on DEV, 0.94846 → 0.95257. That protects against a differently mixed unseen set; it is not a P0 gain.
5. **Scope.** Execution cannot run on the brief's own example query, which is a question about a repository. The README reports 0 of 180 eligible queries on CodeTransOceanDL. Because the FAQ makes the hands-on set APPS-representative, this affects the demo story, not the scoring.
6. **Two choices were made on the test split.** They are bounded: depth 10 → 20 added +0.00458, and numeric comparison added +0.00015.

**My position.** The measured value is the right kind: CPU post-processing that the FAQ explicitly puts in scope, replicates outside APPS, and beats a larger encoder. How large it will be on the unseen set depends on two things: whether the dense pass puts the gold in its top 20, and whether that set contains same-problem near-misses. The weak point is the efficiency of the encoder choice, not the post-processing.

## 3. Arguments

### A. What the brief and the judge ask for
- **Brief, P0:** "Given a library of code and a query in natural language, provide a ranking of the code snippets in order of their relevance to the query."
- **Brief, compute:** "Most retrieval and embedding models are small and fast enough to run on CPU alone. As such, your solution is also expected on run on CPU with minimal GPU resource utilization."
- **FAQ A:** "During retrieval, you should make minimal use of the GPU (ideally use the CPU only)."
- **FAQ B:** "relying on a large model during retrieval is not efficient as this cost is incurred for every query".
- **FAQ, licensing answer:** "The theme focuses on pre/post processing and we don't expect the choice of a embedding/retrieval model to have a significant impact."
- **FAQ 4:** "Dynamic analysis, such as execution of code is also in scope and allowed, however keep in mind that your approach should ideally generalize and not overfit on a dataset."
- **Where the FAQ is silent:** it says the unseen set is "representative of the APPS dataset". It says nothing about how that set is formatted, or whether its corpus holds more than one solution per problem. I do not guess.

### B. Where the measured value comes from
1. **Test split, as the repo reports it** (I did not and may not recompute it): 0.96558 in total, against 0.93756 for the dense pass alone. So about 97% of the score is the encoder. The README says so itself: "the scored gain over the encoder is execution verification alone".
2. **My replay on DEV** (APPS train half, 1.7B, the shipped frozen rule):
   - Dense 0.92792 → 0.94846 (+0.0205).
   - Only 99 of 2,500 statements improve and 3 get worse.
   - In 55 of the 99 improvements, the correct solution was already ranked 2nd or 3rd by the dense pass.
   - TUNE: +0.0160, with 85 up and 3 down.
   - In practice, execution mostly reorders the dense top 3.
3. **The encoder matters more than the pre/post-processing, the reverse of what the FAQ expects** (repo's R2, APPS train DEV):
   - Swapping the 1.7B encoder for the 0.6B costs 0.027 on the dense pass and 0.017 on the whole pipeline.
   - The execution pass adds 0.0205 at 1.7B, so changing the encoder moves the number about as much as all the post-processing does.

### C. Is it the right kind of value?
1. **It is a test oracle, not a relevance model.** It only runs when the query itself contains worked examples.
   - The brief's own example query ("How is the input preprocessed before going to the main function?") gives `has_executable_examples → False`, and so do two repository-style queries I tried.
   - **Conceded:** an unseen set that is "representative of APPS" will probably contain examples. When a query has none, the pipeline falls back to the dense order and loses nothing.
2. **The gain depends on one text layout.** I rewrote only the heading markup of the 5,000 train statements (same words, same examples) and replayed the recorded 1.7B results:

   | heading style | share of the execution gain kept |
   |---|---|
   | Markdown `### Input` | about 16% |
   | `Input:` with a colon | 40–46% |
   | bare `Input` | 40–55% |

   - With Markdown headings, 726 statements lose their examples entirely.
   - In 503 of the 504 statements whose examples change, `### Note` leaks into the expected output, and `compare_output` then rejects even the correct program. So the realistic figure for Markdown is the 16% lower bound.
   - Since the FAQ says nothing about the unseen set's format, this is a risk I have quantified, not a prediction. A regex fix would be cheap, but that is my point: almost all of the post-processing gain depends on one regex parser tuned to CoIR's dashed headings, and when it finds nothing the pipeline quietly falls back to the dense order.
3. **It separates problems, not solutions.**
   - On the CodeContests set, whose corpus includes incorrect solutions to the same problems, execution improves NDCG@10 from 0.721 to 0.754 and rank-1 accuracy only from 0.389 to 0.463. 19 statements improve, 7 get worse, sign-flip p = 0.028.
   - 137 of the 161 wrong programs that "verify" there produce long outputs, meaning they are near-miss solutions to the same problem that pass its sample tests.
   - On APPS, 114 of 148 wrong programs that "verify" match an expected output of 3 characters or fewer (outputs like `YES` or `0`), so those are coincidences.
   - APPS gets away with this because each problem has exactly one solution in the corpus (in the train qrels, 5,000 queries map to 5,000 distinct documents).

### D. Efficiency against the FAQ
- **The scored run used a GPU for queries.** The README says the 0.96558 run "encoded corpus *and* queries on a Kaggle T4."
- **Execution dominated its runtime.** `appsretrieval_results.json` gives `evaluation_time` 12,855.7 s, and `execution_audit.json` gives 11,919.6 s for the execution step alone, which is 92.7%.
- **The encoder is itself a large model at query time.**
  - Per its model card, F2LLM-v2-1.7B is built on Qwen3-1.7B-Base.
  - The repo's CPU benchmark (a 2-core Kaggle machine) measured 7.83 s per query on average, with 8.5 GB peak RAM. That does not fit this 7.7 GiB laptop. I did not re-run it, because loading an encoder locally was off-limits.
- **v2 adds little on the kind of queries the test split has.** On the stdin-style problems that make up ~99% of the test split (repo's statement survey), the candidate configuration against the shipped rule gives:

  | half | NDCG@10 change | statements changed | extra executions |
  |---|---|---|---|
  | DEV | +0.00015 | 3 | +31% |
  | TUNE | +0.0044 | 5 | +28% |

  The team's own estimate (STRESS_TEST F5) is that v2 would change the screening number by about 0.

### E. Concessions
- **Execution is explicitly allowed** by the FAQ.
- **It carried over to a non-APPS source:** +0.034 on CodeContests.
- **It is not fragile to machine load.** I re-timed all 632 correct programs that verify on DEV, one at a time:
  - median 0.072 s, barely above the 0.067 s it takes Python just to start;
  - only 2 take longer than 1 s, and none exceeds 2 s.

  So a slower judge machine is unlikely to change the verdicts that matter, and I drop that line of attack. (This timing is load-sensitive, and another executive was running jobs at the same time.)
- **The README's disclosures are candid.**
- **Contamination:** the OpenCodeReasoning-2 dataset card excludes only "the test split of CodeContests and open-r1/codeforces". It does not say whether APPS test problems were excluded. That source is in F2LLM-v2's training data (per the repo's reading of its paper), so exposure to APPS test problems is unverified either way. The FAQ accepts documented contamination and says it will discount it on unseen data, which puts the 0.937 encoder baseline, the part of the score this architecture did not build, most at risk.

**Position:** the architecture meets P0 by leaning on the encoder, plus one oracle that depends on the dataset's format. What the judge calls the theme's focus contributes one mechanism, and v2 adds little to the screening number while raising the cost.

## 3. Against current best practice (2024–2026)
